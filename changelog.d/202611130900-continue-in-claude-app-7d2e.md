### Added
- (tasks) **"Continue in Claude app…" on a Cursor row, for people who work in the Claude desktop app, not its terminal.** The terminal handoff started Claude Code in a console window; the app's agent cannot be launched from outside, so the Manager does what the app's documented link allows. After the same confirmation it writes the deep brief and conversation file, puts one short message on the clipboard, then asks Windows to open `claude://code/new?folder=<path>&q=<message>` (new `helpers/claude_app.py`: every value URL-encoded on its own, an absolute folder required, a message over 2000 characters refused because the link carries only the instruction, never a brief; the `claude://` handler is checked in the registry first). The order is deliberate: clipboard BEFORE the link, so a link Windows refuses leaves one paste to finish, and the dialog says "Windows was asked to open a new Claude session", never that Claude opened, because `os.startfile` returning means the OS accepted the link and nothing more (a folder opened from a link is also always untrusted, so Claude asks to trust it, and one report says an already-running app may ignore the link). If the brief cannot be written no link is opened. The old entry is renamed "Continue in Claude (terminal)…". Chats whose folder was resolved rather than recorded now follow their resolution for BOTH Claude entries: `project_only` opens the project folder after saying the chat's own checkout was not identified, `ambiguous` and `unmatched` have no folder and say why instead of guessing. Not verified: the link has not been opened on a real machine yet (it needs the live check: app closed vs running, trust prompt, composer filled, and whether the new session can read the brief, the conversation file and the original transcript).
