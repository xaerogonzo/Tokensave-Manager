# What a release contains

The release zip is `Tokensave-Manager-v<version>-windows.zip`, made by `build.ps1 -Release`
(`scripts/make_release_zip.py`). Everything under one versioned top folder,
`Tokensave-Manager-v<version>-windows/`, so unzipping a new version beside an old one cannot
mix two versions' files. `SHA256SUMS.txt` is written beside it, never inside it.

A test (`tests/test_release_contents.py`) fails when a tracked top-level entry has no row in the
second table, when a "No" entry is staged by `build.ps1`, or when a file the zip check requires
is missing from the first table. The page is a guard, not a description someone wrote once.

## Inside the zip

| Path | What it is | The app reads it | Safe for a user to edit |
|---|---|---|---|
| `tokensave-manager.exe` | The GUI, Nuitka onefile | runs | no |
| `tokensave-wrapper.exe` | MCP wrapper Claude Desktop launches | runs | no |
| `tokensave-manager-cli.exe` | The headless CLI (console subsystem) | runs | no |
| `manager-config.example.json` | Annotated template of every key | no | n/a |
| `README.md`, `TOKENSAVE_GUIDE.md`, `CHANGELOG.md` | Documentation; the changelog is the release's notes. `README.md` and `TOKENSAVE_GUIDE.md` are also Help documents, compiled into the GUI | `CHANGELOG.md` shown in-app; the other two no | no point |
| `LICENSE` | MIT licence text | no | no |
| `templates/` | Baseline, gotchas, drive template, release starters; copied recursively | yes: the baseline and lessons are delivered into projects from here | no: edits are overwritten by the next release |
| `docs/` | The Help documents and architecture references (a fixed list in `build.ps1`) | **no**: Help is compiled into the GUI exe; this is a human copy | no point: editing it changes nothing Help shows |
| `docs/help.html` | The Help documents compiled into one self-contained, read-only page (no script, no network); the same page the Help tab opens in a build | **no**: the app opens the copy compiled into the exe | no point: it is generated, and regenerated by every build |

**Not in the zip, and checked not to be:** `logs/` (a run of the app writes it; v2.1.0 shipped one),
any `manager-config.json` (clean or not), and `config-migration.json`. `__pycache__` is skipped when
the archive is written.

### The settings are not in the zip

A packaged Manager keeps `manager-config.json` and its logs in `%LOCALAPPDATA%\TokenSaveManager\`
(`src/config_home.py`), so replacing or moving the program folder never touches them. The zip used to
carry a clean config beside the exe, which overwrote a user's real settings when it was unzipped over an
old folder. It carries none now, and the inventory check refuses an archive that does.

The first start of a build with no settings in the home **copies** the old ones across: beside the
executable first, then the newest sibling `Tokensave-Manager-v<version>-windows` folder. The copy is
verified, appears atomically, never overwrites, and leaves the original where it was; `config-migration.json` in the home records where it came from. A source checkout is unchanged: its
config stays in the repository root.

### Known mismatch

`templates/release/` ships, but the script that adopts it (`scripts/adopt_release.py`) is source-only,
so the starters are reachable only from a checkout. That is deliberate for now (they are for projects
that ship a Windows build, adopted by a developer), and it is listed so nobody assumes otherwise.

## How the build checks itself

`build.ps1 -Release` refuses a working tree with uncommitted changes, stamps the version resource of
all three executables from `constants.APP_VERSION`, then runs `scripts/frozen_smoke.py` on `dist\`
(version resource, CLI from a foreign directory and GUI on a drive script in a first-run state, then the CLI, the
MCP wrapper (sent a real `initialize`) and the GUI again with the real tokensave and git configured, the build's
own templates, and an indexed scratch repository, and finally the GUI as a packaged first run with an old settings
file beside it, which must be copied into the user-data home; each layer its own verdict) and
`scripts/make_release_zip.py`, which checks the archive's inventory and smoke-tests the **extracted** copy
in a folder with a space in its name before it promotes the zip and its checksums.

## The installer

`Tokensave-Manager-v<version>-windows-setup.exe` is made by `build.ps1 -Release -Installer` (`scripts/make_installer.py`, Inno Setup 6) and sits beside the zip, named into the same `SHA256SUMS.txt`. It is compiled from the **validated zip's own contents**, so it holds exactly the inventory the zip check passed: the three executables, `templates/`, `docs/`, the guides and the licence, and no settings.

| | Install | Upgrade | Uninstall |
|---|---|---|---|
| Program (`*.exe`) | per-user by default (no administrator), all-users on request | replaced in place under the same AppId | removed |
| `templates/`, `docs/` | written | **deleted first**, so a file the new version no longer ships cannot linger | removed |
| Settings (`manager-config.json`, `config-migration.json`) | not written; the app creates them in `%LOCALAPPDATA%\TokenSaveManager\` | never touched (they are not in the install folder) | kept; a box, unticked, removes them |
| Logs | not written | never touched | kept; a box, unticked, removes them |
| Projects, indexes, `~\.claude` | not touched | not touched | never touched |

A silent uninstall keeps everything unless `/REMOVESETTINGS=1` and/or `/REMOVEDATA=1` is passed. Removal is confined to a folder named for the application, deletes the settings files and the `logs` folder by name, and removes the folder itself only if it is then empty, so a file a person kept there survives. It does not undo a Claude Desktop registration of `tokensave-wrapper.exe`; the uninstall form says so.

**Tested by really installing it.** Before the shipped installer is compiled, `helpers/installer_drive.py` compiles a TEST build of the same script (its own AppId and data folder), and drives it per-user and silent into a folder with a space: install, the installed application's own smoke test, upgrade over it (a planted stale file must go, settings and logs must stay), and each uninstall option, a file the person kept, and a data folder not named for the application. It refuses to run if the real AppId is registered, and removes only a leftover TEST registration. Not covered: the all-users path (it asks Windows for permission, so it needs a person) and the interactive uninstall form.

The installer is **not signed**: Windows SmartScreen will say "unknown publisher". The checksum and the build attestation say where the file came from, not that a publisher vouches for it.

## The help page

`docs/help.html` is the seven Help documents compiled into one page: a contents list, every document, tables as tables, links that work (`http(s)` and `mailto:` open; links between the documents jump within the page), light and dark by the reader's setting, printable. It has no script, loads nothing, and shows any HTML in a document as text. It is generated by every build from the same function that puts the page inside the GUI executable, so the two cannot differ; the shipped copy describes file locations in general terms, while the Help tab fills in this machine's real paths. A link into the help that points at nothing stops the build.

## Building it on a clean machine

`.github/workflows/release.yml` runs the same `build.ps1 -Release -Installer` on a hosted Windows runner when a
`v<version>` tag is pushed, and creates a **draft** GitHub Release (zip, `SHA256SUMS.txt`, notes from the
CHANGELOG section; zip and setup .exe) after attesting where the files came from. Nothing is published until a person presses
Publish. The runner installs tokensave 7.16.0 and Inno Setup 6.7.3, each pinned by sha256 (the first because the
configured smoke layers need a real one). A pull request that touches the release path runs the build as a dry run.

The Release Wizard (Git tab) hands over to this workflow when the project has one that drafts from a tag: it
checks the tag against the project's version (`scripts/release_info.py check-tag`), writes the CHANGELOG
section, commits, tags and pushes, then stops. It builds nothing, zips nothing and creates no release, and
it refuses to run with the CHANGELOG step unticked, because the workflow takes the notes from that section
and would fail after the tag was pushed. The same goes for notes over GitHub's 125,000-character release-body cap: the CHANGELOG section is the body, so keep it a summary and put long detail under its own heading (2.7.0 did exactly that: a short section, with the full backlog under "Full detail of this release"). A project without such a workflow keeps the whole pipeline. The
workflow's draft job still refuses to touch a release that already exists (made by hand, say): delete it
(keep the tag) and re-run the job.

What this does not do: it does not sign anything (Windows SmartScreen will say "unknown publisher"), and a checksum detects a damaged
download, not who published it.
