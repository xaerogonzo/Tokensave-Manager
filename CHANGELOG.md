## [Unreleased]

### Added
- (vscode) **The extension's user-visible surfaces are tested in a real editor.** It has 18 commands, a tree view, a webview, a status bar and a diagnostics collection, and `test/vscode-stub.js` says in its own header which of those it does *not* cover — the tree and the command wiring. Those were verified by a person opening a window and looking, which is slow, subjective, and stops happening exactly when the project gets busy. `@vscode/test-electron` now boots VS Code with the extension loaded and runs 32 assertions holding the real `vscode` module. `activate` returns a narrow `TestApi` whose `renderTree` yields **rendered strings** — indentation, label, description — because `getTreeItem` decides label, description and icon together, and a test asserting against the `Node` union behind it passes with all three wrong. The single deliberate widening is `treeCommandFor`: the "Manager CLI unavailable" row's whole value is that clicking it opens the fix, and a row rendering "click to fix" while wired to the wrong command is a defect no string assertion can see
- (vscode) **A mutation runner, because a suite that passes on its first run is what a suite testing nothing looks like.** Booting a real editor makes it *look* convincing, and looking convincing is not evidence — so each protected property is removed from the compiled output and the test written for it must object, by name. **13/13 arms are caught by their own test.** It earned its place immediately: the status-bar pin test was decorative **three times**, and each fix looked sufficient. With one workspace root, "pinned to a folder" and "follows the active editor" name the same folder. With two roots that were merely both dirty, the bar rendered the same marker either way. And a predicate waiting for "the bar says something" was satisfied by the *startup* render, so the assertion ran before the editor had moved — passing against mutated code in 256 ms. The generalisable lesson, now in `docs/VERIFICATION.md`: **asserting that something did not change needs an observable transition to wait on**, or the wait is satisfied by the state that was already there
- (vscode) **A smoke suite against the packaged `.vsix`**, because the live suite loads `out/` through `--extensionDevelopmentPath` and users install an archive. `.vscodeignore` decides what ships and `vscode:prepublish` decides what is compiled first, so a mistake in either produces an extension that passes every test and is broken on install. `--disable-extensions` **inverts** between the two paths: correct for the development-path suite, it switches off an extension that is genuinely installed, and VS Code has `--disable-extension <id>` but no positive form to pair with it. The packaged runner therefore omits the flag and takes its isolation from a fresh `--extensions-dir` holding exactly one extension. Found by watching every assertion fail on a missing command — a failure that reads as the extension being broken rather than absent
- (vscode) `DEVELOPMENT.md` — which suite a new test belongs in, and the gotchas that cost the most to rediscover: two live suites share `.vscode-test/` and must not run concurrently, an interrupted run leaks an editor that holds the workspace open (with the command to kill it), and the webview's page script lives inside a TypeScript template literal where a backtick in a *comment* closes the string
- (hooks) **`helpers/git_hooks_env.py` — where git will *actually* look for a hook, and who owns it.** Both hook modules defined "installed" as *the file exists at `<project>/.git/hooks/<name>` and carries our marker*, which is the wrong predicate twice over, and both failures are silent while the Manager shows a ✓. `core.hooksPath` **replaces** the hooks directory rather than adding to it — git resolves every hook from there with no fallback — and tokensave 7.11.0's global `githooks on` sets it, so accepting that offer switches the Manager's own pre-commit and pre-push off in every repository on the machine without touching either file. The module asks git (`git rev-parse --git-path hooks`, measured against git 2.55.0) instead of composing a path, and reports the facts — effective directory, raw `core.hooksPath`, the config scope that set it, and ownership — rather than a verdict. Ownership is decided by resolved paths and exact markers, never by looking for "tokensave" in a string: `C:\Tokensave\hooks`, a UNC share and a relative `relative/hooks` would all match a substring test while meaning different things, and — the one that actually bites — **the Manager's own marker is `# TOKENSAVE-PRECOMMIT-MARKER`**, so a case-insensitive search reports the Manager's hooks as tokensave's and sends a user to run `tokensave githooks off` to fix something tokensave never wrote
- (hooks) **`INERT` as a first-class state, distinct from "not installed".** A hook on disk that git is ignoring needs the *routing* fixed; re-installing writes the same bytes to the same ignored place, reports success, and changes nothing a commit would notice. Both toggles — the Git tab's pre-commit button and the Checks dialog's pre-push button — used the boolean as install/remove and would have "installed" over an inert hook; they now explain what is wrong instead. `is_*_hook_installed` answers "will it run", so it is False for `INERT`, and callers needing to tell absent from ignored use the state function
- (verification) **A geometric oracle, and the first committed drive scripts this project has had.** The harness could drive the UI and photograph it but not *assert* anything, so every live check was written once, read once and thrown away — four defects reached users through a green suite that way (the doc-drafter tab strip needing 760px against its own 720px minsize, Draft PR buttons squeezed off-screen, the gitignore Save bar pushed off-screen, the Test Gaps list clipped). `helpers/geometry.py` is pure predicates over rectangles that **measure no fonts**, because a predicate resolving its own text widths is a claim about the machine running it — a headless runner's default font can be twice the real width. `helpers/geometry_scan.py` reads real laid-out geometry and returns the **population it measured** alongside the findings: "no findings across 214 widgets" and "no findings across 0 widgets" are the same empty list and different claims. Reachable live as `{"do": "report", "what": "geometry"}`, with committed scripts in `scripts/drive/`
- (verification) `docs/VERIFICATION.md` — which technique owns which failure class, and what this project's guards are actually worth. All six `test_no_*` guards were mutation-tested and **6/6 caught their defect**, recorded because it contradicts the expectation that this finds a vacuous guard nearly every time; plausibly this project is the exception because `f8e0a09` already taught it that lesson at cost

### Fixed
- (docs) **The upgrade-audit runbook was sending every audit to read a file that had not existed for months.** `docs/UPGRADE_INTEGRATION.md` step 4 said to scan `helpers/daemon_cost.py` for wrappers of removed tools; v2.4.0 deleted that module — the release that deleted it is three entries below in this file. Nothing failed, because a step naming a missing file reads as "nothing to check there". It now names the modules that actually wrap tokensave, and says in the document that this list rots and must be updated in the same commit as any rename
- (docs) **`docs/ARCHITECTURE.md` did not mention the extension at all.** `vscode-extension` appeared zero times in a document whose purpose is the repository tree, while the extension had grown to 18 commands, four npm test scripts and a mutation runner. Its helper count was also two short (82 against 84 — already stale by one before this roadmap), the upstream-issues listing predated four archivings, and `helpers/git_hooks_env.py` was missing
- (savings) **"Cache reads: not reported" was a permanent claim, and tokensave 7.11.0 disproved it.** 2.4.0 recorded that the field could not exist and could not be derived — `sum(by_model.tokens) - (input + output)` was *exactly zero* on every payload — and hardcoded `cache_read_tokens = None` with a docstring explaining why it would stay that way. Upstream #472 (filed from this repo) now exports `total_cache_read_tokens`, `total_cache_creation_tokens` and a `total_tokens` summing all four, and `by_model` counts the same four so the payload's own cross-check reconciles. The three surfaces that rendered the words — the CLI envelope, the Cost panel and the extension's savings webview — read the number when it is there. The field stays `int | None` rather than becoming an `int`: a 7.10 binary is still a supported input, and "this binary did not say" must not collapse into "zero", which is the whole three-value contract the module exists to keep
- (savings) **The "$361.51 per million tokens, which matches no Claude price" finding was a short denominator, not a pricing anomaly.** Counting only input and output, this machine reads **$272–$342/Mtok** across ranges; counting all four categories it reads **$0.58–$0.65/Mtok**, stable at every range. So the figure was never evidence about tokensave's pricing — three quarters of the tokens were missing from the divisor, because the dominant category is cache reads and they were not in the export. `implied_usd_per_mtok` now returns `(rate, basis)` as one value, so a 7.10 figure and a 7.11 figure cannot be rendered as the same statistic, and the panel says which denominator produced the number
- (savings) **`cost`'s `tokens_saved` became range-scoped, and is still not the project figure.** Upstream #473 (also filed from here) fixed the lifetime-counter-for-every-range bug: today 97,704 / 7d 550,983 / 30d 876,775 / all 31,322,215 where 7.10 returned one number four times. It is now displayable — but it equals `gain --all` **exactly** at every range and does *not* equal project-scoped `gain` (7d: 550,983 against 19,644 here), because `cost` has no project filter. Publishing the number alone would have moved the old scope ambiguity into the envelope, so it ships with `tokens_saved_spans_range` and a test fails if either ever appears without the other
- (hooks) **The Manager's git hooks could never work in a linked worktree.** `<worktree>/.git` is a *file* pointing at the shared metadata, so `os.path.join(worktree, ".git", "hooks")` names a path under a file: the directory cannot be created, every install failed, and `is_installed` then reported "not installed" forever. Git keeps one hook directory per repository, resolved through `--git-common-dir`; measured on a main checkout plus two linked worktrees, all three resolve to the main checkout's `.git/hooks` while `--git-dir` differs for each. Same root cause as the `core.hooksPath` blindness above — a composed path instead of an asked one — and fixed by the same call
- (tests) **The import-time path guard was scanning 71% of `src/` and never said so.** It skipped the entire `dialogs.*` package — 43 of 160 modules — because those "import tkinter at module level which crashes on Linux CI without DISPLAY". Both halves were wrong: importing tkinter needs no display, only constructing a widget does, and none of the 43 constructed one at import (the two candidates sit inside `if __name__ == "__main__":`). The modules it removed were precisely the population the guard exists to protect, since the failure it catches "invisibly breaks the `fake_home` fixture for all dialog tests". Nothing was hidden on the day, but a quarter of `src/` was unreachable for anything added later. Blanket rule replaced by a per-module `_KNOWN_UNIMPORTABLE` list with a reason per entry and a staleness test, in the shape `test_no_console_flash` already used for `_EXEMPT`. Population 114 → 157, and CI confirmed it holds on Linux
- (tests) **The same guard reported findings but never its population.** It printed "N module(s) skipped as unimportable" while the test asserted only the exit code, so stdout was never read on the passing path and the diagnostic that would have shown it is skip-marked by default — a walk yielding nothing would have produced no offenders and passed. It now emits `SCANNED_MODULES=` on every path including failure, asserts it against a floor, and exits `2` when it cannot import part of its population, so an inconclusive run can never be read as clean
- (verification) The collapse predicate could never fire on a real widget: **Tk clamps a zero-width widget to 1px**, so `w < 1` is correct in the abstract and dead in practice. Found by pointing the oracle at the running app rather than by any of the 25 green unit tests. Threshold now lives in the toolkit layer at 2px, with separators and sizegrips exempt, and the check requires the widget to carry content — an empty container at 1px is Tk working correctly, which is what the first live run reported on the Help tab's per-section footer

## [2.4.0] — 2026-08-29

### 2.4.0 — savings that are actually savings, and a Manager you can talk to

- (savings) **The Cost panel was reporting money *spent* as money *saved*.** It scraped `tokensave cost`'s human table for the Cost column — API list price for traffic that had already happened — and rendered it in a card labelled "Value Recouped". On the reference machine that read **$4,132.75** where `tokensave gain`, the ledger that actually records savings and was never called, said **$0.14**. "Saved Tokens" was no better: a lifetime, all-projects counter shown under a "past 7 days" subtitle. Savings now come from `gain` (per-project, with an explicit all-projects toggle) and spend from `cost` (machine-global — tokensave offers no project filter, so the heading says so inline). Their ranges move independently, because `cost` writes to tokensave's global ledger and a range selector wired to it would turn a display control into repeated ingestion
- (savings) **Cache reads are reported as "not reported", never as a number.** The obvious derivation — `sum(by_model.tokens) - (input + output)` — is *exactly zero* on every payload, so a panel computing it would have rendered `Cache reads: 0` forever while `tokensave cost`'s own cache-hit column read 100%. That is a fabricated figure in the code written to stop fabricating figures. The spend section also states outright that its cost cannot be derived from the token counts beside it, so a user checking the arithmetic blames the right party
- (cli) **`READ_ONLY_COMMANDS` promised something two of its members did not keep.** `cost` and `discover` ingest accounting rows into `~/.tokensave/global.db`, and `doctor` rewrites `~/.tokensave/state.toml` (content-identical, mtime only) while touching neither the database nor its WAL — so a WAL-only check would have cleared it. Replaced by a three-way classification (`PURE_READ` / `OBSERVE_REFRESH` / `MUTATING`) whose every member was measured against an idle control run rather than assumed, and which defines `PURE_READ` as no *data* mutation so `focus`'s window-raising is not read as a stronger claim than it makes
- (cli) **Four surfaces named the same operations and drifted silently.** `cli.py`'s subcommands, the generated VS Code tasks, the extension's command ids and the IPC actions now all derive from one table in `helpers/commands.py`, including a checked-in generated `commands.ts` that a test fails on the moment it goes stale — a "generated" file nobody verifies is a hand-maintained file with a misleading header
- (manager) **The Manager can now be asked to open a dialog, instead of having a file written that nobody notices.** A request inbox under `.tokensave-manager/requests/` is drained on its own light timer. Propose-only holds absolutely: every action opens a window in front of a person, and none commits, applies or approves. The payload is treated as untrusted input — allowlisted actions, per-action schemas, canonicalised project paths checked against the configured search roots, and commit files required to live inside the project they name. An acknowledgement is written *before* the pending file is deleted, because "the file is gone" cannot distinguish drained from rejected, quarantined or never-filed
- (cli) **`status` now names the changed files, and it costs nothing.** The porcelain-v2 parser was already walking every per-file record to decide `dirty` and throwing the paths away. It also gained `-z`, without which `core.quotePath` — which defaults to *true* — C-quotes any non-ASCII path and a rename hides its original path behind a TAB. `status.mcp` also reports `probed: false`, so a consumer cannot render a bare "MCP OK" from what is only a reading of a file on disk
- (vscode) **Four new surfaces**: a status bar pinned to a folder rather than following the active editor (an item whose subject changes as you navigate is never *known* to be wrong), a commit composer that reports delivery from the acknowledgement ledger rather than assuming it, a savings view as a `WebviewViewProvider` under a nonce CSP with separate text and attribute escaping, and per-file `checks` / `test-gaps` actions
- (cli) **`--paths` scopes findings without changing their shape.** A path outside the project is an error rather than an empty result, because silently returning zero findings for one is indistinguishable from a clean file; `requested_paths` and `matched_paths` let a consumer tell "this file is clean" from "that path is not part of this project". Diagnostic replacement takes an explicit scope, so a run about one file cannot clear findings in files it never looked at
- (cli) **`test-run` now says *why* it could not verify a result.** `passed`/`failed`/`skipped` cannot distinguish "your tests failed" from "pytest never started" from "the Manager killed it on a timeout", and the remedies differ. A `run_state` field names which, falling through to `unreadable` rather than assigning a cause it has not earned
- (upstream) **Three tokensave accounting bugs found along the way**, filed as aovestdipaperino/tokensave#472, #473 and #474: the cost export's token fields cannot account for its own cost (the tool's `--by-agent` view reports ~599x more raw tokens for the same window), `tokens_saved` is byte-identical for every range and disagrees with `gain` by ~2.15x, and `discover`'s token estimates are 1.45–47 tokens per turn. Drafts kept in `docs/upstream-issues/`; absolute usage totals were replaced with rates and ratios before filing
- (chore) `helpers/daemon_cost.py` is deleted — its table-scraping regex is what produced the original bug. Suite 2752 → 2993 passing, extension tests 49 → 82

## [2.3.1] — 2026-08-27

### 2.3.1 — two things 2.3.0 got wrong, found by running it on a real project

- (cli) **`test-run` reported "could not verify the result" for a project that simply has no Python tests.** pytest collected 0 items and said so — `===== no tests ran in 0.17s =====` — which is a result, read successfully. But `_parse_pytest_summary` scans for `passed`/`failed`/`error` and that footer contains none of them, so it returns `(0, 0)`: the same value it returns when the output could not be read at all. The command then took the second reading. That is precisely the conflation `EXIT_VERIFY_FAILED` was added to prevent, committed by the code enforcing it. A run pytest positively reports as empty is now `EXIT_OK` with `collected: 0`; a timeout or a crashed collection still exits 4. Surfaced on a **PowerShell** project with a `tests/` directory — the kind of tree the Python-shaped assumption never considered
- (cli) **`--base origin/master` was a hardcoded default that is wrong on every repository using `main`** — and before 2.3.0 it failed *silently*, because a diff against a ref that does not exist yields no changed files and renders as "0 test gaps". 2.3.0 made it refuse, which is how it was found. The default is now `auto`, which reads `refs/remotes/origin/HEAD` — the answer git already holds, not a guess between the two names. An explicitly named base is still honoured exactly as given and never replaced, `auto` refuses rather than trying candidates when the repository will not say, and a bad explicit ref now names the branch that would have worked
- (cli) **`doctor` reported 12 stale projects as 10, because tokensave truncates its own list.** The output shows ten bullets and then `… and 2 more`, and `parse_stale_entries` counts bullets — so the header, which carries the authoritative total and whose regex *already captured it*, was discarded. `stale_count` is now that number, `stale` remains what could be named, and `stale_truncated` says when the two differ. Presenting the shorter list as the whole story is the same class of error as reporting an unverified scan as clean
- (cli) **`scout` ignored the suppressions made in the Manager's dialog.** It called `run_scout` with no ignored set, so a finding dismissed with the Ignore button came straight back in the editor — making the button look broken, and splitting the two surfaces the single findings contract exists to keep together. It now reads `refactor_scout_ignored` from the Manager config
- (vscode) `tokensaveManager.testGapsBase` defaults to `auto` to match

### Roadmap-13 — one findings contract, and three formats that were not what they looked like

- (cli) **One `findings` array, three producers, one consumer.** `checks` (pyflakes + compileall), `doctor` (the cap audit) and the new `scout` all emit the same record — `file`, 1-based `line`/`column` plus a required `end_line`/`end_column`, a closed-set `severity`, `message`, `rule`, `symbol` — and the VS Code extension renders all three identically without knowing which command produced them. The shape is modelled on `refactor_scout.Finding`, which already carried most of it, rather than invented alongside it. It sits **top-level in the envelope, not inside `data`**, because it is a cross-command contract while `data` is per-command payload, and it is always present — an empty list where there is nothing to say — so no consumer branches on absence. Additive, so `schema_version` stays 1; the rule is now written down (adding an optional field is compatible, removing/renaming/retyping is not)
- (checks) **The extension could never show more than one problem, and nobody had noticed.** `run_pyflakes_check` returns `(bool, summary)` where the summary is the first line plus `"(+N more)"`, and the CLI put that string in `data.pyflakes.output` — so a project with forty warnings reported one. Both tools are now run once and their raw output feeds two branches: a structured `Finding` list, and the same one-line summary the Manager's dialogs have always shown. The truncation is deliberate on the legacy branch and is now asserted, so a later "simplification" cannot quietly change the Run Checks dialog
- (checks) **Three output formats were captured rather than remembered, and all three differed from the obvious guess.** The fixtures under `tests/fixtures/quality_checks/` are real tool output, and each one exists because it broke something: (1) a `compileall` block can have **no `File "..." line N` line at all** when the error precedes a position — a parser requiring it drops the finding entirely; (2) the `*** Error compiling '...'` header prints a **`repr()`** with doubled separators while the `File` line prints the path **raw**, in the same block, so feeding the raw one to `ast.literal_eval` turns a separator before `b` or `t` into a backspace or a tab and sends the editor to a file that does not exist — caught by the fixtures after being written that way first; (3) pyflakes writes a second, **column-less** format to **stderr** for files it could not analyse at all, and concatenating the streams reports an unreadable file as a lint warning. The streams are now parsed separately, which is the tool's own distinction rather than an inference: stdout is a warning, stderr is an error
- (checks) **`compileall`'s caret does not give a usable column, and the position is line-level on purpose.** The caret aligns to the *stripped, re-indented* source line the tool prints, not to the file: an open paren at real column 13 inside an indented method prints its caret at offset 5. Recovering the true column would mean re-reading the source from a pure parser, and would be wrong anyway if the file changed since — so column 1 is reported rather than something confidently wrong. pyflakes reports the same error at the correct column, so both findings are kept and each names its source
- (doctor) **Cap violations became records and can now be clicked to a line (R12-10).** The auditors walk AST nodes and always had `node.lineno`; they discarded it while formatting a string. `Violation(file, symbol, line, message)` keeps it, and `__str__` reproduces the previous text exactly — verified against the pre-change implementation on this repository's own tree: **152 violations, strings byte-identical**, with all four renderers (the Doctor tab, the Run Checks dialog, the pre-push hook, and the *generated* CI workflow snippet) left untouched. The audit is wired into `doctor` as **advisory**: it emits findings but never moves the exit code, because this project already runs it `continue-on-error` in CI and 144 findings on a healthy tree would otherwise make the command permanently red
- (cli) Four commands: **`scout`** (refactor candidates straight from the tokensave index — no LLM; the model only enters when a user clicks Investigate in the Manager), **`status`** (a deliberately closed roll-up: branch, dirty, index counts, MCP verdict, pending request — and nothing that walks the tree), **`tests`** (AST-only discovery, counts exact and lists capped so a large repo cannot hand an editor a 50,000-entry payload), and **`test-run`** (structured `passed`/`failed`/`skipped`/`duration_seconds`, so the extension never parses pytest text)
- (cli) **`status` never probes, and there is a test that says so.** `effective_scope` spawns `claude mcp get` with a cwd, and invoking Claude Code in a directory it has not seen CREATES a project entry — this Manager littered `~/.claude.json` with eight duplicate keys exactly that way. `status` is the one command a UI may call on refresh, so it probing would rebuild that problem at a much higher rate. Its lifecycle is written down too: one call on activation, one per explicit refresh, debounced on watcher events, and never on a tree redraw
- (cli) **`test-run` takes a per-project lock, using an OS file lock rather than a PID file.** The tempting design records the owner's pid and checks liveness, which needs two things this project cannot have cheaply: a portable probe (`os.kill(pid, 0)` is the POSIX idiom, but on Windows signal 0 is `CTRL_C_EVENT`, so it *signals* the process instead of probing it) and a process start time to tell a live owner from a recycled pid. An advisory lock on an open descriptor is released by the kernel however the process exits, so there is no stale-lock question and no identity to get wrong
- (cli) **Three existing contracts said things that were not true.** `sync` now reports `changed` as **three-valued** — `true`/`false`/`null` — parsed from tokensave's own `N added, M modified, K removed` summary, because a caller deciding whether to refresh must not read "we could not tell" as "nothing happened". `commit-request`'s docstring claimed byte-identity while the code compared three fields and the writer re-serialised without `sort_keys`; identity is now a hash of a normalised payload, which also fixes a latent bug where the reader stripped whitespace from paths and the comparison did not, so a trailing space made a request differ from itself. And `test-gaps --base` now verifies the ref exists: `git diff` against a missing ref yields no changed files, which rendered as "0 test gaps" — the most reassuring possible way to report that the question was never asked
- (vscode) **Findings land in the Problems panel**, with squiggles on the line each refers to. Results are swapped in **when a command finishes, never cleared when it starts**, so a long Scout run leaves the previous findings visible rather than showing an unearned clean bill of health. Each command owns only its own results: re-running Scout never disturbs Checks, and neither touches a sibling workspace folder even when both contain a file at the same relative path. `test-run` deliberately produces no diagnostics — a failing test is not a statement about a line of source, and a red suite would bury the findings that are
- (vscode) **A missing `schema_version` used to be accepted as version 1.** The check was `envelope.schema_version > SUPPORTED_SCHEMA`, and `undefined > 1` is `false` in JavaScript, so a malformed payload sailed through. The window is now explicit and closed: missing rejects, `1` accepts, above and below reject

### Roadmap-12 — VS Code integration, and two premises that did not survive measurement

- (vscode) **The integration needed far less code than planned, and finding that out was the work.** The plan's Phase C — a `mcp_vscode.py` schema adapter, a `${workspaceFolder}` binding, a `.vscode/mcp.json` writer, a gitignore negation — is **not built, because measurement showed none of it is necessary.** A scratch harness with two deliberately mismatched projects (7 files / 14 nodes against 23 / 46) and probe-named servers established that **one root `.mcp.json` serves BOTH the Claude Code extension and Copilot Agent Host**. VS Code files that workspace file under the category "Built-In" and names the source `workspace-dot-mcp` in its own logs; the Manager already writes exactly that file. Deleting planned work because the experiment removed the need for it is the outcome the measure-first structure existed to allow
- (vscode) **"VS Code MCP" is not one thing, and the client that matters most does not use it.** Three separate definitions live on a typical machine — `%APPDATA%\Code\User\mcp.json` (a `servers` + `inputs` schema), `~/.copilot/mcp-config.json` (`mcpServers`), and the project's own `.mcp.json` — with different consumers. The Claude Code extension reads **none** of VS Code's: it contributes no MCP settings, its `jsonValidation` claims `.claude/settings*.json`, its bundled schema is keyed on `.mcp.json`, and a grep of its 3.0 MB bundle finds `mcpServers` ×34 with **zero** hits for `.vscode/mcp`. Confirmed behaviourally — a session in the scratch project answered from the right tree (`db_size_bytes` byte-exact) while a same-named server planted in VS Code's user file never appeared, even under a deliberate name collision
- (vscode) **The bare `serve` in VS Code's user config does not shadow the way Claude Desktop's did — it crashes.** This work opened by calling those entries "structurally identical to the pathology retired in PR #18", with the verdict explicitly deferred to measurement, and the measurement disagreed. VS Code spawns MCP servers with **`cwd` = the user's HOME directory**, so tokensave finds no index there, refuses to guess among the registered projects, and exits 1. It has never served anything — which is also why Copilot has never had tokensave tools. Desktop resolved a global pin and answered confidently from the wrong repository; this one answers nothing at all. The Manager must therefore say "this entry has never worked", never "this entry is shadowing", and the Desktop retirement copy must not be reused for it
- (build) **`_BASE_DIR` had been resolving to the current working directory in every frozen build.** `constants.py` asserted that "NUITKA_ONEFILE_PARENT is the actual .exe path"; measured against Nuitka 4.1 with a probe build, its value is the parent process **PID** (`'41108'`). Running a bare number through `dirname(abspath(...))` resolves it against the current directory, so a packaged Manager read `manager-config.json` and wrote `logs/` wherever it happened to be launched from. It went unnoticed because the usual launch path has the exe's own folder as the cwd. Now `_resolve_base_dir(env, argv0, module_file)` using **`sys.argv[0]`**, which IS the bootstrap path under onefile — `sys.executable` is not a substitute, as it points at the temporary extracted binary. The same silent-cwd-inference failure class as the MCP scope collision, so it is pinned by tests rather than merely fixed
- (cli) A headless surface, `src/cli.py`, with its contract fixed up front because three consumers will depend on it: **stdout carries exactly one envelope and nothing else**, stderr is human-only, and exit codes are semantic (0 ok / 1 found problems / 2 usage / 3 prerequisite / 4 unverified) so a caller can distinguish "doctor found problems" from "the CLI itself failed" without scraping text. An invalid invocation leaves stdout **empty** rather than emitting half a payload, and an unexpected exception still yields a valid envelope — a traceback on the machine-readable channel is unreadable garbage to a parser. `--project` is **required** on every command: a process's working directory is not a statement about which project the user means, and that inference is not being reintroduced in the Manager's own tooling
- (cli) `commit-request` refuses to overwrite a differing pending request without `--replace`. A pending request is work the user has not yet approved in the Manager, and silently replacing it would discard their queue — the policy fired for real during testing, declining to clobber a 17-file request
- (cli) `mcp-status` reports its layers separately and **does not probe `effective_scope` unless asked**. That probe spawns `claude mcp get` with a cwd, and invoking Claude Code in a directory it has not seen CREATES a project entry — this Manager littered `~/.claude.json` with eight duplicate keys in exactly that way
- (cli) `--config <path>` lets a relocated CLI be pointed at an install, keeping the "explicit beats inferred" rule rather than having it search. The default — read the config beside the executable — is unchanged for a normal install
- (build) A third build target, `tokensave-manager-cli.exe`, built `--windows-console-mode=force`. The console mode is the point rather than a detail: the other two targets are built `disable`, and such a binary has **no stdout at all**, so the CLI's entire contract would be unreachable through them. Recorded in `docs/ARCHITECTURE.md` because `build.ps1` is gitignored, and a regenerated script would otherwise lose the target silently
- (services) `helpers/sync_service.py` and `helpers/doctor_service.py` extracted so the controllers and the CLI share **one implementation each**. `sync` was controller-owned and `doctor` was split across both; a CLI that re-derived either would guarantee Manager-behaviour and CLI-behaviour quietly diverging. `doctor_ctrl.py` 1003 → 802 lines
- (vscode) `.vscode/tasks.json` generation, reachable from Projects → right-click → 📂 Open. Tasks are `"type": "process"`, never `"shell"` — a shell task re-parses its command line, so an executable under `D:\Claude Co worker\...` is split at the space, a failure this project has already reported upstream once. Every task passes `--project "${workspaceFolder}"`, and a frozen runner is not offered a `checks` task it could only ever fail
- (vscode) Click-to-open on refactor-scout findings, which carry `file` and `line`. Doctor violations are plain strings with no line number, so they cannot use it without resolving the symbol first — the plan assumed both surfaces could be wired, and only one can
- (vscode) A VS Code extension (`vscode-extension/`). It runs the Manager's **live `src/cli.py`** by default — point `tokensaveManager.managerPath` at a checkout — rather than a bundled binary. A compiled CLI is a snapshot taken at build time and needs a rebuild-repackage-reinstall cycle before the editor catches up; source mode has none of that, needs no `configPath` (the CLI finds the config beside the checkout), can run `checks` (which a frozen build cannot, since `sys.executable` under onefile is the extracted binary), and drops the package from ~14.6 MB to ~14 KB. A bundled exe remains the fallback for machines with no checkout. Deliberately a **thin shell**: it runs the CLI, parses one envelope and renders it, and reimplements none of the tokensave attribution, MCP precedence, Doctor rules or test discovery that live in the Manager — a second implementation in TypeScript would just be a second thing to be wrong. - (docs) `docs/vscode-mcp-matrix.md` records the per-client chain (client → host → consulted sources → effective source), with sanitised JSON fixtures under `tests/fixtures/vscode_mcp/`. Two guards were verified by deliberately breaking them: a machine path in a fixture fails, and a verdict backed only by `config`-tagged evidence fails — the second encodes the lesson from the Desktop investigation as a test rather than a note

### Roadmap-11 — the third gate: Claude Desktop's own tokensave

- (mcp) **Three sessions reported a stale index, re-synced, and stayed wrong. It was never staleness — the MCP server was serving a different repository.** In OpenChem Studio it cost four queries before the diagnosis was believed: `compute_aromaticity`, `compute_joback` and `compute_griffin_hlb` all returned `[]` — one written minutes earlier, one four commits back, one shipped long ago — while `status` reported `active_branch: "main"` for a repo whose default is `master`. **Three misses in a row is not staleness, it is a different tree.** The tell that settles it: after a re-sync `status` comes back byte-identical — same `last_sync_at`, same node count — while `uptime_secs` has reset, so the server restarted and reopened the *same wrong database*
- (mcp) It reproduced in this repo while the fix was being planned. MCP reported 741 files / 24,530 nodes / branch `joback-thermophysical`; the CLI reported 307 / 9,813 / `Roadmap-11`. The MCP `db_size_bytes` of 93,863,936 was a byte-exact match for OpenChem Studio's `tokensave.db`. **`db_size_bytes` is the cheapest way to identify which tree you are actually being served**
- (mcp) The mechanism: Claude Desktop registers its own `tokensave` in `claude_desktop_config.json` and spawns the manager's wrapper **app-level, not per session** — both live wrappers had `ppid` = the Desktop process. The wrapper therefore cannot know which repository a session is in and resolves one from the global pin; every Desktop-hosted Claude Code session inherits that single server; and Claude Code dedupes MCP servers by name, so it beat each project's own `.mcp.json` — which was running correctly beside it the whole time. **One pin, N repos, so multi-project was structurally impossible.** A scope collision, not a binding problem: every binding on the machine was already correct
- (mcp) **Three existing defences could not have caught it, and each for a structural reason worth keeping written down.** `strict_tree` was `true` in *both* projects and did nothing — the server opens one project's index and reads *that project's* config, so it believes it is serving correctly; it guards `graph_root` redirection inside a server, not which repo the client is in. `claude mcp get` reads `~/.claude.json` and never Desktop's config, so the entry was invisible to the tier added for exactly this class of question. And a cwd rule in the wrapper is impossible, because its parent is the app rather than the session — now recorded in the wrapper itself so the next reader does not try
- (mcp) Retiring the entry is its own guarded migration, never a side effect of binding a project, because it **removes a feature**: Claude Desktop chat loses tokensave entirely. That trade is deliberate and the confirmation says so in those words. Four things that would each have made it unsafe: Desktop rewrites its config from memory every 1–2 minutes, so retirement is refused outright while it runs — as a disabled Apply, not a banner, with Desktop distinguished from Claude Code by **executable path** because both ship as `claude.exe` and a name check would block the migration permanently, the user being in Claude Code to perform it; both physical config files must change on a UWP install, the package copy and the `%APPDATA%` copy being one logical configuration seen from two process contexts; every target is re-read and re-digested immediately before writing, so a file that moved between preview and click refuses the whole operation rather than half-applying it; and Undo restores the **verbatim** prior entry rather than a reconstructed canonical one, declining a file edited since
- (mcp) The flag records **intent, not absence**, which is what makes a reappearance detectable: entry absent plus retired is quiet, absent and never migrated is informational, present and never migrated offers the migration, and present *after* retiring is reported as a regression — an app update or a hand edit can do that
- (mcp) **A shadow verdict is relative to the project being inspected.** A running Desktop wrapper is not inherently a fault; it is a fault only when it wins the `tokensave` name for one project while serving another. Five states, and the guard that matters is the one asserting the *absence* of a warning: a wrapper serving project A must not be reported as shadowing A. Without it the new rule would have fired loudest against the one project that works, and this Doctor has already had to be fixed once for nagging. The evidence hierarchy is preserved — wrapper record / `-p` argument above `-shm` mtime correlation — so a `-shm` match reports "cannot determine which project it serves", never a confirmed shadow
- (daemon) **Process enumeration had been silently returning nothing inside the manager, and nobody had noticed.** `_enumerate_windows` spawned a bare `"powershell"`, so `CreateProcess` depended on PATH and the resulting `OSError` was swallowed into `[]` — indistinguishable from "found none". The new Desktop panel made it visible by printing both halves at once: *"no Desktop tokensave server is running"* beside *"could not determine whether Claude Desktop is running"*, while two servers were running. **This also means the Tokensave Daemon Manager dialog had been listing zero servers the whole time.** Resolved through `shutil.which` with an absolute System32 fallback — the lesson `effective_scope` already recorded for `claude` — plus `stdin=DEVNULL` and a `strict` mode raising `EnumerationFailed`, so "failed to ask" is never again reported as "asked and found none". Two other hypotheses were eliminated by measurement first: pythonw stdio inheritance works fine even fully detached (`stdin: None`), and CIM is 0.34s and unaffected by four-way concurrency
- (mcp) **A retired entry read as missing — again.** Immediately after retiring, the Claude Desktop block went red with *"No 'tokensave' MCP server is configured"* and an **Apply this fix** button that would have put the shadowing entry straight back, in the same dialog whose next panel reports the migration complete. The user-scoped migration had already solved exactly this; both now share `_retired_absence()`, whose comment records that four surfaces read that verdict. Settings stopped claiming tokensave "routes through the manager's pin-aware wrapper", and the header badge separates `pinned · serves MCP` from `manager default` — the pin is **not** obsolete, `project_discovery` still consumes it, so only its MCP meaning was retired
- (mcp) The Stop confirmation was promising something that never happens. It told the user a session "will reconnect, and may restart the server automatically"; for a Desktop-spawned server Desktop reports it disconnected and leaves it. Stopping stays visible, confirmed and transitional, never automatic — an auto-kill would turn "serving the wrong tree" into "no tokensave at all", which from the user's seat is indistinguishable from tokensave randomly breaking
- (ci) **Linux CI caught a bug the local suite structurally could not.** `os.path.normcase` lowercases on Windows and is a **no-op on POSIX**, and the UWP-shape test compared a normcased path against the lowercase markers `"packages"` and `"claude_"`. On Linux that was permanently False, so the `%APPDATA%` view was never marked active and dropped out of the change set — the half-applied migration the module exists to prevent, passing locally purely because this machine is Windows. Lowercased explicitly now, because recognising the *shape* of a Windows path must not depend on the host OS; path equality still goes through `normcase`, which is correct where the filesystem is case-insensitive. `test_active_uwp_detection_does_not_depend_on_normcase` patches `normcase` to identity so the failure reproduces on Windows too — verified against the pre-fix code, where it fails `1 == 2`
- (verification) Three layers, all required to agree, because configuration-only checking is precisely what failed: **config truth** (the project's `.mcp.json` resolves to project scope), **process truth** (the live server belongs to that project), and **behavioural truth** (MCP `tokensave_status` matches direct CLI status). Verified end to end after retirement: MCP reports `Roadmap-11`, 307 files / 9,813 nodes, matching the CLI, with a single `tokensave serve -p .` and no wrapper servers, and a symbol written minutes earlier resolves. It took effect **without** a full Desktop restart, which the plan had assumed would be required

- (mcp) The binding is a project-root `.mcp.json` holding `{"command": "tokensave", "args": ["serve", "-p", "."]}` — **no machine paths, nothing project-specific**, so the file is genuinely shareable through version control rather than a local file wearing a shared file's name. Both halves of that shape were measured, not chosen: `${CLAUDE_PROJECT_DIR:-X}` proved to resolve to **X** (the variable is not set at config-resolution time and appears nowhere in a live session's environment), while `-p .` works because Claude Code spawns a project-scoped server with cwd = the project root. - (mcp) Scope is derived from the path plus a real `.tokensave/` directory — never the filename alone, which would let a stray `somewhere/.mcp.json` be judged by project rules and offered a binding for a project that does not exist. Deriving it from the argument meant no signature changed and none of the five existing consumers were touched. - (mcp) Retiring the user-scoped entry is a guarded migration, never a side effect of binding one project: every project must be bound or explicitly skipped, **and at least one actually bound**, or "skip everything then remove" would leave no tokensave anywhere. ### Roadmap-10 — Phase 10: the pin watcher was wrong, and the restart was never necessary

It reads “🛡 Enable strict_tree…” or “… Disable …” depending on the selected project's actual state, read at popup time rather than when the menu is built — the menu is constructed once and reused for every row, so a value captured at build time would be stale for all but one project. ### Roadmap-10 — Phase 9: the windows that flash

- (subprocess) Thirteen console windows opened across the screen every time the manager started, one per indexed project, in a two-second burst. `Launch TokenSave Manager.bat` runs the app through `python_exe`, which is **pythonw.exe** — an interpreter with no console — and on Windows a console child of a console-less parent is given a **brand-new console window** unless the parent passes `CREATE_NO_WINDOW`. Redirecting the child's stdio does not prevent it, which is the part that makes this easy to miss: `capture_output=True` looks like it should already be enough. Measured directly — parent console handle `0`, child without the flag `console_hwnd=83169620`, child with it `0`
- (subprocess) The startup burst was `claude_tasks.scan_worktrees` running `git worktree list --porcelain` once per project. Found by instrumenting `Popen.__init__` and launching the real app, after a static approach failed to settle it: only 31 nodes are reachable from `App.__init__` in the call graph, because it does not follow Tk dispatch or thread targets, so reading the code could not tell which of the candidates actually ran at startup
- (subprocess) An AST audit of all 133 call sites in `src/` found 18 missing the flag; 11 were real and now pass it, across `claude_tasks`, `tasks_tab`, `update_poller`, `checks_dialog`, `multi_remote`, `quality_checks`, `worktree_cleanup` and `precommit_review`. The other 7 are left alone deliberately and the reasons are recorded rather than assumed: five sit in the POSIX arm of a `sys.platform == "win32"` split whose Windows arm uses `os.startfile`, and two more launch the Claude CLI with `CREATE_NEW_CONSOLE` on purpose — there the console *is* the feature, and suppressing it would be the regression
- (subprocess) Fixing it also made startup measurably faster, which was not the goal. The unflagged calls went from ~170 ms each to ~37 ms; the flagged `git status` calls in the same runs took the same time before and after, which rules out filesystem-cache warmth and attributes the ~130 ms to console allocation itself. Roughly 1.6 s off every launch. It also explains the reported symptom that the rectangles get briefer on repeated launches — the git call underneath speeds up with a warm cache while the window creation stays constant, so the console is on screen for less time
- (tests) `test_no_console_flash.py` guards it, because the failure is invisible in development: run the same code under `python.exe` — a pytest run, a terminal launch — and the child inherits the existing console, nothing flashes, and the bug cannot be reproduced. Exemptions are keyed by function rather than line so ordinary edits do not rot them, each carries its reason, and two further tests check the guard is actually matching calls and that every exemption still points at real code
- (tests) Test runs flashed windows too, from an unrelated cause. `conftest` withdraws the Tk **root**, which hides the root and nothing else — a `Toplevel` is a sibling window, not a child widget, so it maps and paints regardless. Instrumenting a full run: **162 Toplevels constructed, 162 mapped**, across 161 tests. Every dialog test drew a real window for as long as the test took
- (tests) They are made transparent (`-alpha 0.0`) rather than withdrawn, and the difference matters: a withdrawn window reports `winfo_viewable() == 0` and `winfo_ismapped() == 0` and loses its position, and dialogs read all three — `_centre_on_parent` measures itself, and sizing code waits on mapping. A transparent window is still mapped, still viewable, still where it was put, and simply cannot be seen. The suite passes identically with and without it, which was the constraint. `TOKENSAVE_SHOW_TEST_WINDOWS=1` restores the old behaviour for anyone who wants to watch a dialog build

- (pin-watcher) Changing the active project now takes effect on Claude Desktop without restarting it, when switched on in Settings. The watcher notices the change, ends the stale server, and lets Desktop's own supervisor start a fresh one on the new pin
- (pin-watcher) This was deferred in `docs/MCP_INTEGRATION_GOTCHAS.md` as "Option A", blocked on one thing: *"the watcher needs a reliable way to discover the tokensave PID"*. - (pin-watcher) It kills a live MCP server, so what it **won't** touch is the larger half of the design. Only a server carrying a wrapper run record — proof the manager started it — and only when that record's project differs from the new pin. A `heuristic`, `ambiguous` or `unattributed` row is never retired: a pin change is not new evidence, and the four-state contract exists so a guess never becomes a kill. The third branch is deliberately unchanged, because with nothing routed through the wrapper there is no server to retire and a restart genuinely is the answer. Auto-detect was checked and also left alone: the watcher no-ops on a *cleared* pin, so its “restart to trigger a fresh auto-detect” was already correct

The historical CHANGELOG entries describing the revert are left as they are: they record what was true when written

All four fail against the pre-fix code

It used to kill the stale server and print “Claude Desktop will restart it on the newly pinned project” — a claim nothing checked. The case that hides is the expensive one: when Desktop does not come back, the user is left with **no** tokensave server where before they had a stale one, and the log said it worked. Not hypothetical either — the in-wrapper version of this feature was reverted precisely because Desktop could fail to complete the MCP handshake with a respawned wrapper. `_await_respawn` now watches for up to 15s and reports what actually happened, naming the consequence rather than the fault when it did not: restart Desktop, because until you do there is no tokensave at all
- (pin-watcher) Success requires a server that was **not already running**. Desktop keeps more than one up, so if a sibling was already serving the newly pinned project then “a server on the new pin exists” is true the instant you look — reporting that as a respawn would be the same unchecked optimism in better disguise. The live PIDs are captured before the kill and a match against one of them does not count. A mutation test removes the check and confirms the test written for it then fails
- (pin-watcher) The wait sits in the polling loop rather than in `tick()`, keeping the module's existing split intact: `tick()` is the decision function and every decision in it stays testable without threads or sleeping, which a fifteen-second block in the middle of it would have ended. ### Roadmap-10 — Phase 3: multi-remote push

- (git) Push and Force Push now go to every remote you select, reported per remote in one dialog rather than N popups. "Push targets…" (right-click or shift-click the Push button) picks them. The saved selection is reconciled against `git remote` on every use, so a remote renamed or deleted outside the manager drops out instead of failing at push time — or worse, quietly shrinking the push while still reporting success for what remains
- (git) **Upstream tracking is a separate question from "who receives this push."** Looping `push -u` over N remotes would leave the branch tracking whichever finished last — a silent edit to the user's git config, made by a button that only said "push". Exactly one remote (or none) is nominated for `-u`; the rest get a plain push. Nominating a remote you are not pushing to is cleared on save, since git would never update that tracking ref anyway
- (git) **Force-push leases against each remote's own current tip**, read immediately beforehand with `git ls-remote`. Bare `--force-with-lease` leases against the *local* remote-tracking ref, which a rarely-fetched remote may not have at all and a stale one describes days-old state — so the protection the confirmation dialog promises was quietly not applying to precisely the remotes most likely to have diverged. A branch the remote has never seen leases on "must not already exist", which is a real lease rather than an unprotected push wearing the name. A remote that cannot be consulted is **skipped, not force-pushed**: not knowing what would be overwritten is a reason to stop. There is no `--force` fallback anywhere, and a test asserts it across every path
- (git) A remote is not a URL. Git allows several `pushurl` entries per remote and pushes to all of them, so results are parsed per destination out of git's own `To <url>` blocks — reporting `origin ✓` while one of its two destinations was rejected would be a lie
- (scrub) After a history rewrite, the post-push message names every remote that was **not** updated and says the scrubbed content stays recoverable from them. It is a warning rather than a success box when any exist: for a privacy scrub, an un-rewritten remote is not a loose end to mention in passing, it is the content still being published. The pre-push confirmation warns about them too. Previously both talked only about `origin`
- (git) Remote URLs are redacted wherever they reach a dialog, a log line or a result string. `git remote -v` returns `https://user:token@host/...` verbatim if that is how the remote was configured, so any URL originating from git config is treated as possibly secret-bearing. Pasting a credentialed URL into the setup wizard is refused outright, rather than written into `.git/config` where every later command would repeat it
- (remotes) The GitHub setup wizard is now provider-driven: `dialogs/remote_setup.py` holds the wizard, `helpers/remote_providers.py` holds what differs between GitHub, GitLab and Codeberg. `GitHubSetupDialog` remains as a thin subclass so every existing caller is untouched, and its release command is pinned argv-for-argv against what it built before the split — a generalisation is only worth anything if the path it generalised still runs the same commands
- (remotes) Codeberg is deliberately CLI-less. Forgejo's CLI story could not be verified against a live instance, and the alternative — inventing a token flow from documentation and having the manager hold the secret — is what the credential rule forbids. Pushing works today through git's credential helper, and the wizard says so plainly instead of offering a login button that does not exist
- (settings) GitLab CLI (`glab`) detection, mirroring how `gh` is found. Detection rather than a configured path, because that is how every other forge CLI is located here

### Roadmap-10 — Phase 2: shadow links (SL2 + SL3)

- (shadow-links) "Keep shadows fresh on every sync" — opt-in per project. Files added after a manual run were never shadowed, so a new `.zsc` silently dropped out of the index with no signal that anything was missing. Runs before the sync rather than after, so the new links exist for the indexer about to read them. Off by default, and the cost when off is one small file read: the tree walk and the hardlink probe both sit behind the flag
- (shadow-links) The sync log reports only what can be acted on. A volume without hardlink support is silent — that is a property of the disk, not an error, and repeating it every sync trains you to ignore the log. Files *failing* on a volume that does support links is the opposite and now warns: previously the rule was "log only when created > 0", under which a permissions or filesystem problem presented as "auto-shadow appears to do nothing at all"
- (shadow-links) Stale-shadow detection, gated on provenance rather than filename shape. A hardlink outlives its source: delete `Blood.zsc` and `Blood.zsc.cpp` remains, so the index keeps serving code with nothing behind it. But a file matching that pattern may equally be the user's own work, and **nothing on disk distinguishes the two** — so the saved map now records the paths the manager created, and only those are ever offered for cleanup. Anything else is labelled a candidate whose origin cannot be proven, and is left alone
- (shadow-links) Four states, because "shadow file" was hiding four different situations: **healthy** (same inode), **suspicious** (both files exist but are no longer the same inode — an editor that saves by replacing breaks hardlinks silently, and the replacement may be deliberate, so this is diagnosed and never touched), **stale** (source gone, we recorded creating it), **candidate** (source gone, no record). `os.path.samefile` decides sameness; `st_nlink` is supporting evidence only, since a link count of 2 says the inode has two names *somewhere*, not that these two paths are the pair
- (shadow-links) The saved map is written atomically (temp file + `os.replace`). SL2 rewrites it on every sync, and a crash mid-write would leave a truncated file that reads as "no saved map" — silently discarding both the user's extension map and the provenance record that makes cleanup safe
- (shadow-links) Saving from the dialog preserves the provenance list rather than replacing the whole file, and drops entries for mappings the user removed. Without that, one Apply would turn every recorded shadow back into an unprovable candidate and disable cleanup for that project permanently
- (doctor) Warn-only shadow-link health in the Doctor report: stale links, broken links, and unprovable candidates, each with what to do about it. Silent for projects with no saved shadow map, so projects not using the feature do not gain a line about it. Lives in the stdlib-only `doctor_rules`, so it runs on the headless CI runner too; deliberately not counted as a cap violation, since a stale shadow is a fact about the working tree rather than a code-health defect

### Roadmap-10 — Phase 1: worktree + daemon lifecycle

- (tasks) Deleting a worktree that fails now reports what is actually true instead of advising a retry that cannot work. `git worktree remove` **deregisters the worktree even when it cannot delete the folder**, so the old "close things and try again" left the user looping over a command with nothing left to do, on a directory whose `.git` file now points at pruned metadata. `WorktreeRemoveResult` re-runs `git worktree list` and reports registration as an observation; the exit code and stderr are treated as what git *attempted*
- (tasks) The leftover folder is offered for inspection before deletion, and deletion is a second, separate confirmation. It usually holds the uncommitted work that caused the delete to fail, so "git forgot about it" is not treated as evidence it is disposable. A directory signature (file count, total size, newest mtime — ignoring `.git`/`.tokensave`/`__pycache__` churn) is captured when the half-state is first seen and rechecked immediately before deleting: if the user kept working in there, the delete refuses
- (tasks) The two lock holders are distinguished, because their remedies differ: an error naming `.tokensave/tokensave.db` is a server holding the index and is fixable; one naming the bare folder is a live session's own working directory and clears when that session exits. `lock_kind` is parsed from stderr and marked **evidence only** in the result contract — it explains, it never decides
- (tokensave) 🔌 Manage servers… in Tool Manager. `tokensave serve` reports nothing about itself and most instances carry no project argument (measured: two of eight declared `-p`), so servers are attributed at four confidence levels and the Stop control differs for each: declared → stop; matched by timing → stop only behind a confirmation naming the project and saying plainly it is a guess; unidentified or ambiguous → disabled, with the reason shown. Deliberately **no "Stop all"** — Claude Code respawns its MCP servers, so it would not converge and would churn live sessions
- (tokensave) Attribution for bare servers correlates each project's `tokensave.db-shm` mtime against process start time — SQLite stamps that file when it opens the database in WAL mode. Its documented failure mode is asserted rather than hoped: a second server attaching to an already-open database restamps nothing, so it reports `unattributed` instead of inventing an answer. Servers that declare `-p` double as free ground truth, and a test cross-checks the heuristic against them — which is what caught the bug below
- (tokensave) Fixed a start-time conversion that made the correlation silently useless: subtracting a local-midnight epoch from a local `CreationDate` produced a value off by the whole UTC offset — 14400 s here, 7200× the match tolerance. Every timestamp match failed and every bare server came back unidentified, with nothing raised. A structural test pins the fix, because the test that found it can only run where servers exist
- (proc) New `helpers/proc_kill.py` folds two kill implementations that looked interchangeable and were not: one killed a process **tree** immediately, the other **one** process gracefully. Merging them naively would have stopped the smoke runner reaping child pytest processes and turned daemon stops immediate, so both axes are parameters (`tree`, `graceful`) with the existing callers' argv- and signal-level behaviour pinned by tests
- (proc) Killing verifies process identity first, because a PID is not one: a process can exit and the OS reissue its number, so a Stop clicked against a stale row could hit a stranger. On Windows a single handle is opened, checked (creation time + image) and terminated — reuse cannot redirect a handle. POSIX uses `pidfd` where the kernel has it. Where neither is available the fallback verifies then signals by PID, and **says so in its result** rather than reporting a guarantee it did not provide; tree kill is PID-resolved by nature and documented as such

### Roadmap-10 — Phase 0: the cross-thread guard's second blind spot

- (tests) `test_no_cross_thread_tk.py` reported zero offenders while 101 real cross-thread Tk calls sat in the tree. ### Fixed (Roadmap-5)

The manager was reading `os.path.getmtime(tokensave.db)` exclusively, so a project that had been actively used and synced minutes ago would still display "6h ago" or similar. `find_projects` now takes the max mtime across `tokensave.db`, `tokensave.db-wal`, and `tokensave.db-shm` — whichever was touched most recently wins. Restoring the column to actually reflecting "when was this index last poked".
- **`tokensave-wrapper.py` Popen now passes `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` explicitly — fixes MCP connection timeout that was actually a stdio-inheritance bug, NOT a threading bug as previously believed.** Symptom: Claude Desktop banner `Could not attach to MCP server tokensave`; per-project `mcp-logs-tokensave/*.jsonl` reporting `Connection timeout triggered after 30040ms (limit: 30000ms)`. Diagnosed by running the wrapper directly with `subprocess.PIPE` stdio and feeding it a real MCP `initialize` request — the default `Popen(args, creationflags=CREATE_NO_WINDOW)` (no stdio args) produced zero bytes from tokensave, while the same call with explicit `stdin=sys.stdin, stdout=sys.stdout, stderr=sys.stderr` returned a full valid initialize response in <100 ms. Root cause: when pythonw.exe (windowless subsystem) spawns a console subprocess, Python's default stdio inheritance doesn't propagate the parent's piped standard handles to the child reliably. Explicit pass-through forces Python to extract the underlying OS handles from `sys.std*` (which DO have the pipes Desktop set up) and supply them as the child's stdio. Works under both `python.exe` (console launch) and `pythonw.exe` (windowless launch). This bug almost certainly existed in the wrapper before — production installs that hit it were probably using the DXT extension shape (running `tokensave.exe` directly, no wrapper) which doesn't have the indirection. Pin-file watcher / live-reload remains deferred; will be reattempted out-of-process so the wrapper stays single-threaded.
- **Reverted `tokensave-wrapper.py` to the literal original 12-line shape — the earlier daemon-thread pin-watcher broke MCP handshake on Claude Desktop UWP installs.** Symptoms: `Could not attach to MCP server tokensave` banner; per-project `mcp-logs-tokensave/*.jsonl` reporting `Connection timeout triggered after 30040ms (limit: 30000ms)`. Wrapper was successfully spawning the tokensave child each time and the child stayed alive for ~60 s — but the MCP initialize handshake never completed within Desktop's 30 s deadline. Root cause appears to be a stdio-inheritance interaction with pythonw.exe when threading is imported and a daemon thread is alive: tokensave receives no MCP messages from Desktop. Removing the import of `threading`/`time` and the daemon thread restores the proven-working 12-line wrapper Desktop reliably attaches to. **Consequence**: live in-session pin reloading via wrapper-side file watch is deferred. - **MCP configurator now correctly targets Claude Desktop's actual config file on UWP / Microsoft Store installs.** Claude Desktop ships in two layouts: a traditional installer that uses `%APPDATA%\Claude\claude_desktop_config.json`, and a Microsoft Store / UWP package (e.g. `Claude_pzs8sxrjxfjjc`) that uses `%LOCALAPPDATA%\Packages\Claude_*\LocalCache\Roaming\Claude\claude_desktop_config.json`. **The two paths can both exist on disk as different physical files**, because Windows applies asymmetric file-path redirection: a UWP-context process opening `%APPDATA%\Claude\` gets redirected to the package's LocalCache, while a non-UWP process opening the same path string sees a separate "external" file. Both files report the same path string when listed but contain different bytes. Diagnosed when a user's manager Apply correctly wrote 231 bytes of canonical wrapper-routed content to `%APPDATA%\Claude\` while Claude Desktop continued spawning `tokensave.exe -p <hardcoded>` from a 2,219-byte UWP-internal file the manager had never touched. Falls back to the traditional path when no UWP install is detected. A 50-line `_watch_pin` daemon thread now polls `~/.tokensave/desktop-project.txt` every 2 seconds; when the mtime changes to a different valid project, it terminates the current `tokensave serve` child and the outer respawn loop spawns a new one pointed at the new project. ### Fixed
- **`_do_git_commit` no longer runs `git reset` before staging.** The original reset was there to "clear the index so nothing already-staged sneaks into the commit" — but the cost was destroying intentional stagings like `git rm --cached` (the untracking operation the new 🧹 flow performs). The new behaviour: skip the reset entirely, use `git commit -m <msg> -- <paths>` (path-specific commit) so only the listed paths land in the new commit regardless of what else might be in the index. Standard git pattern; makes the index-reset unnecessary.
- **`_do_git_commit` no longer blindly `git add`s every selected file.** Files that are already fully staged (xy column 1 == `' '`, e.g. a `git rm --cached` queued by 🧹 Untrack Ignored Files appears as `D ` — staged-delete with no working-tree change) don't need re-adding. Worse: calling `git add` on a staged DELETION un-does the deletion and tries to re-add the file, which fails if the file matches a `.gitignore` rule — leading to the exact failure mode the 🧹 flow was supposed to prevent. Fix: GitCommitDialog now passes `(fname, xy)` tuples to the worker, and the worker only calls `git add` on files whose xy column 1 is not space.
- **Better error surfacing when `git add` does hit an ignored file** (e.g. user explicitly ticked an already-tracked-but-ignored file in the dialog). Previously the manager just logged `git add failed: <raw git output>`. Now it detects `ignored by one of your .gitignore files` in the output and shows a dedicated dialog with the affected paths listed and a one-line action to fix it.

### Added
- **Pre-flight tracked-but-ignored check in `_open_commit_dialog`.** Before opening the commit dialog, the manager runs `_find_tracked_but_ignored(path)`. If any matches exist, it shows a 3-way choice: **Yes** → open Untrack Ignored Files first (recommended); **No** → open the commit dialog anyway; **Cancel** → close, do nothing. This proactively breaks the cycle instead of waiting for the commit attempt to fail.

### Internal contract changes
- `GitCommitDialog` callback signature is now `callback(path, message, selected: list[tuple[str, str]])` — each tuple is `(fname, xy)`. The old `list[str]` form is still accepted for backward-compat (unknown XY is treated as needs-add, which is harmless because git add is idempotent).

## [1.0.1] — 2026-05-21

Patch release. Fixes the three bugs hit during the very first post-v1.0 retrofit attempt: a status-text parsing off-by-one that ate leading dots, a baseline `.gitignore` that over-corrected on `.codegraph/`, and the missing "Untrack ignored files" flow that left users stuck whenever a path was both tracked and ignored.

### Fixed
- **`git status --short` parsing dropped the leading character of the first file** when that file's status was working-tree-modified (`" M file"`).
